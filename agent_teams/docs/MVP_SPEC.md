# MVP_SPEC

## 0. 목표 사용자 · 해결할 문제 · 성공 시 결과

- **목표 사용자:** 코드리뷰/이슈 요청이 여러 건 동시에 쌓이는 팀의 리드 또는 팀원. "지금 뭐부터 봐야 하는지, 누가 맡았는지"를 빠르게 파악해야 하는 사람.
- **해결할 문제:** 요청이 목록으로만 나열되면 우선순위(P0/P1/P2)·리뷰 필요 여부·담당·다음 액션이 한눈에 안 보여 놓치거나 중복 확인하게 된다.
- **성공 시 사용자가 보는 결과:** 화면 진입 즉시 전체 요청 목록이 보이고, 목록에서 항목 하나를 고르면 그 항목의 우선순위·리뷰 필요 여부·담당·다음 액션이 상세 영역에 즉시(추가 로딩 없이) 표시된다. 사용자는 클릭 한 번으로 "이 요청, 지금 내가 뭘 해야 하나"를 확인할 수 있다.

## 1. 요구사항 목록 (필수 vs POST_MVP)

### 필수 (MVP)

- **REQ-001**: 화면 진입 시 요청 목록이 렌더된다. 각 목록 항목은 최소 제목과 우선순위 배지를 보여준다.
- **REQ-002**: 목록에서 항목을 클릭(또는 키보드로 선택 후 Enter)하면 해당 항목이 "선택됨" 상태가 되고, 상세 영역에 그 항목의 우선순위(P0/P1/P2)·리뷰 필요 여부·담당자·다음 액션이 표시된다.
- **REQ-002a**: 상세 영역의 리뷰 필요 여부를 표시하는 요소는 `data-needs-review="true"` 또는 `data-needs-review="false"` 속성을 반드시 가진다(선택된 항목의 `needsReview` 값과 일치). 표시 문구(예: "리뷰 필요"/"리뷰 불필요")는 자유롭게 정할 수 있으나 이 속성은 문구와 무관하게 항상 존재해야 한다 — 자동 테스트는 문구가 아닌 이 속성 값으로 검증한다(Tester [CHALLENGE] 반영, 제안 1 채택).
- **REQ-003**: 목록 항목이 하나도 없을 때(빈 상태) 목록 영역과 상세 영역에 각각 명시적인 빈 상태 안내가 표시된다.
- **REQ-004**: 화면 진입 시 아직 아무 항목도 선택하지 않은 상태(초기 상태)에서는 상세 영역에 "왼쪽/목록에서 항목을 선택하세요" 안내가 표시되고 우선순위·담당 등 필드는 표시되지 않는다.
- **REQ-005**: 데이터는 **완전 정적** mock 데이터(JS 객체 배열, 페이지 로드시 코드에 이미 10~15개 항목이 하드코딩되어 있음)로 제공한다. 실제 GitHub/이슈 트래커 연동은 하지 않는다. 사용자가 화면에서 새 요청을 추가·수정·삭제하는 입력 폼은 MVP에 포함하지 않는다(POST_MVP-6, 아래).
- **REQ-006**: 선택 상태는 목록에서 시각적으로 구분된다(선택된 항목에 표시 스타일 적용).

### POST_MVP (이번 실습 범위에서 제외)

- **POST_MVP-1**: 우선순위/담당자 기준 필터링 또는 정렬 UI. (이유: §2.1 상한상 핵심 상호작용은 1~2개로 제한 — "선택→상세 보기"를 1번째 핵심 상호작용으로 확정하면 필터는 2번째 후보이나, 사용자 원문에 명시되지 않아 임의 추가하지 않음. 아래 "질문 후보" Q-003 참고.)
- **POST_MVP-2**: 다음 액션 완료 처리(체크/토글), 담당자 재배정 등 상세 영역 내 편집 기능.
- **POST_MVP-3**: 실제 GitHub Issues/PR API 연동, 인증, 실시간 동기화.
- **POST_MVP-4**: 다중 페이지·라우팅, 알림, 정렬 히스토리.
- **POST_MVP-5**: 검색어 입력을 통한 목록 필터링.
- **POST_MVP-6**: 사용자가 화면에서 새 요청 항목을 추가/수정/삭제하는 입력 폼. (Researcher [CHALLENGE] 반영 — mock 데이터 방식은 A안 "완전 정적"으로 확정. B안 "화면에서 직접 추가"는 사용자 원문에 없는 별도 상호작용이라 §2.1 상호작용 1~2개 상한 보호를 위해 POST_MVP로 명시적으로 내림. AGENT_RESOLVABLE로 자체 판단, Main 재조정 가능.)
- **POST_MVP-7**: 모바일/좁은 화면 대응(반응형 레이아웃 전환). (Researcher 권장 및 Main 승격 요청 반영 — 아래 §7, Q-005 참고. 데스크톱 전용을 MVP 기본으로 확정하고 모바일은 별도 화면 전환 로직이 필요하므로 POST_MVP로 내림.)

## 2. 핵심 사용자 흐름 (단계별)

### Flow A — 목록 탐색 → 상세 확인 (REQ-001, REQ-002, REQ-006)

1. 사용자가 index.html을 연다 → 목록 영역에 mock 요청 항목들이 나열된다(REQ-001). 상세 영역은 초기 상태(REQ-004)를 보여준다.
2. 사용자가 목록에서 항목 하나를 클릭한다(또는 Tab으로 포커스 이동 후 Enter/Space).
3. 클릭된 항목이 선택됨 스타일로 바뀐다(REQ-006). 이전에 선택된 항목이 있었다면 선택 해제된다(동시에 선택 항목은 항상 0개 또는 1개).
4. 상세 영역이 즉시 갱신되어 선택 항목의 우선순위·리뷰 필요 여부·담당·다음 액션을 보여준다(REQ-002).
5. 사용자가 다른 항목을 클릭하면 3~4단계가 반복되고 상세 영역 내용이 새 항목 것으로 교체된다.

### Flow B — 빈 데이터 상태 (REQ-003)

1. mock 데이터 배열이 비어 있는 경우(개발/테스트 조건), 목록 영역에 "표시할 요청이 없습니다" 같은 안내가 나타난다.
2. 상세 영역은 초기 상태와 동일한 자리에 빈 상태 안내를 보여준다(선택 가능한 항목이 없으므로 항상 초기/빈 상태 유지).

## 3. 화면 구성과 UI 영역

단일 화면(1 view). 구조는 아래 semantic 영역으로 구성한다 (정확한 DOM 배치·CSS는 Builder Planner 소관, 여기서는 역할·표시 조건만 계약).

| 영역 | 역할 | 표시 조건 |
|---|---|---|
| **Toolbar/Header** | 앱 제목 표시("코드리뷰/이슈 요청 대시보드" 등 문구는 Builder 재량, 존재는 필수) | 항상 표시 |
| **목록 영역 (List)** | mock 요청 항목을 세로 목록으로 렌더. 각 항목에 제목 + 우선순위 배지(P0/P1/P2) 최소 표시 | 항상 표시. 항목 0개면 빈 상태 문구로 대체 |
| **상세 영역 (Detail)** | 선택된 항목의 우선순위·리뷰 필요 여부·담당·다음 액션 표시 | 3가지 상태 중 하나: (a) 초기(미선택) — 안내 문구만, (b) 선택됨 — 4개 필드 모두 표시, (c) 빈 데이터 — 안내 문구만 |
| **Status 영역(선택)** | 총 요청 건수 등 요약(예: "총 N건") | 항상 표시 가능(선택 사항, MVP 필수 아님 — 있으면 좋음 정도) |

- 상세 영역은 **오른쪽 고정 패널**로 확정한다(DEC-001, DECISION_LOG.md). 목록과 상세는 항상 좌우로 나란히 표시되며, Drawer/모달/아코디언 방식은 채택하지 않는다.

## 4. 사용자 동작별 결과 화면 변화

| 동작 | 트리거 | 결과 |
|---|---|---|
| 목록 항목 클릭 | mouse click 또는 keyboard Enter/Space (포커스된 항목) | 해당 항목 선택됨 스타일 적용, 상세 영역이 그 항목 데이터로 갱신, 이전 선택 해제 |
| 같은 항목 재클릭 | 이미 선택된 항목을 다시 클릭 | 상태 변화 없음(선택 유지, 토글로 선택 해제하지 않음) — 이 동작은 MVP 확정: 재클릭은 아무 효과 없음 |
| 페이지 새로고침(F5) | 브라우저 새로고침 | 선택 상태는 **항상 초기화된다**(DEC-002, DECISION_LOG.md 확정). 새로고침 후 상세 영역은 REQ-004 초기 상태로 복귀하며, 선택 항목을 localStorage 등으로 유지하는 기능은 구현하지 않는다. mock 데이터 자체는 코드 내 정적 배열이므로 항상 동일하게 재로드됨 |

## 5. 상태 명세

- **초기 상태(Initial):** 페이지 로드 직후, 아직 아무 항목도 클릭되지 않음. 목록은 모든 mock 항목을 표시. 상세 영역은 "목록에서 항목을 선택하세요" 문구만 표시(우선순위/담당 등 필드 요소 자체가 DOM에 없거나 비어 있음 — Builder Planner가 selector로 확정).
- **빈 상태(Empty):** mock 데이터 배열 길이 0. 목록 영역에 "표시할 요청이 없습니다" 문구 표시. 상세 영역은 초기 상태와 동일한 문구 표시(선택 불가능하므로 항상 이 상태 유지).
- **오류 상태(Error):** 외부 API를 쓰지 않으므로 네트워크 오류 케이스는 없음. 단, localStorage 접근 실패(브라우저 프라이빗 모드 등 예외 상황) 시에도 앱은 깨지지 않고 정적 mock 데이터로 정상 동작해야 한다(REQ-007로 아래 추가). localStorage 저장은 "있으면 좋음"이고 실패해도 핵심 기능(목록/상세 보기)은 유지되어야 한다.
  - **REQ-007**: localStorage 접근이 실패해도(또는 사용하지 않기로 결정되어도) 목록 표시·항목 선택·상세 보기 기능은 정상 동작해야 한다.
- **선택/활성 상태(Selected):** 정확히 0개 또는 1개 항목만 선택 가능(다중 선택 없음). 선택된 항목은 시각적으로 구분(예: 배경색·테두리 — 구체 스타일은 Builder 재량이나 "구분되는 스타일이 존재해야 한다"는 조건은 필수). 상세 영역에 4개 필드(우선순위/리뷰 필요 여부/담당/다음 액션) 모두 표시. 리뷰 필요 여부 요소는 REQ-002a에 따라 `data-needs-review="true|false"` 속성을 반드시 가진다.
- 로딩 상태는 해당 없음(정적 데이터, 네트워크 호출 없음이므로 로딩 스피너 불필요).

## 6. 데이터 모델 (mock, 정적 JS 배열 기준)

각 요청 항목 필드 정의 (Builder Planner가 실제 변수명·구조를 확정하되 아래 필드는 반드시 포함):

| 필드 | 타입 | 값 범위/설명 |
|---|---|---|
| `id` | string/number | 항목 고유 식별자 |
| `title` | string | 요청 제목 (예: "PR #123: 로그인 리팩터링") |
| `priority` | string enum | `P0` \| `P1` \| `P2` (필수, 목록·상세 양쪽에 표시) |
| `needsReview` | boolean | 리뷰 필요 여부 (true/false). 표시 문구는 Builder Planner 재량(예: "리뷰 필요"/"리뷰 불필요")이나, 테스트 가능성을 위해 상세 영역의 해당 요소(예: `#detail-needs-review`)에 `data-needs-review="true"` 또는 `"false"` 속성을 반드시 함께 부여해야 한다(REQ-002a, 아래) |
| `assignee` | string | 담당자 이름 (mock 문자열, 담당자 없음 케이스는 "미배정" 같은 명시적 값으로 표현) |
| `nextAction` | string | 다음 액션 설명 (mock 문자열, 예: "테스트 케이스 보완 후 재요청") |

- mock 데이터는 코드 내 정적 배열로 최소 5~8개 항목을 포함해 P0/P1/P2가 골고루 섞이도록 구성한다(Builder Planner가 실제 값 채움).
- 필드 값이 비어있는 경우(예: assignee 없음)는 데이터 자체에 명시적 문자열로 채워 UI에서 별도 "값 없음" 분기를 만들 필요가 없도록 한다(mock이므로 항상 값 존재를 보장).

## 7. 반응형 — 데스크톱 전용 확정 (DEC-003)

이 MVP는 **데스크톱 전용**이며, 반응형 대응(모바일/좁은 화면용 레이아웃 전환)은 전혀 구현하지 않고 **POST_MVP-7로 완전히 분리한다**(DEC-003, DECISION_LOG.md 확정). 브레이크포인트·모바일 전용 뷰 전환 로직·`matchMedia` 분기 등은 이번 MVP 범위에 포함하지 않는다.

- **MVP 확정 동작:** 뷰포트 폭과 무관하게 목록 영역과 상세 영역은 항상 좌우 2-컬럼(오른쪽 고정 패널, §3 DEC-001)으로 동시에 표시된다. 화면이 좁아져 레이아웃이 압축되거나 가로 스크롤이 발생하는 것은 허용하되, 이를 보완하는 별도의 좁은 화면 전용 UI/로직은 만들지 않는다.
- **POST_MVP-7:** 좁은 화면(모바일)에서 목록↔상세를 전환하는 반응형 레이아웃(Microsoft List/Details 패턴 근거, RESEARCH_REPORT.md §4). 이번 실습 범위에서는 착수하지 않으며, 향후 별도 요구사항으로 재검토한다.
- 접근성 요구(§8)는 화면 크기와 무관하게 그대로 유지한다(키보드 탐색·aria-selected 등은 데스크톱 전용 여부와 별개의 필수 요구).

## 8. 접근성 요구

- 목록은 semantic list 구조(`<ul>`/`<li>` 또는 동등한 role)를 사용하고, 각 항목은 버튼 또는 focusable 요소여야 한다(Tab으로 도달 가능).
- 목록 항목은 키보드 Enter 또는 Space로 선택 가능해야 한다(REQ-002 마우스와 동등).
- 선택된 항목은 `aria-selected="true"` 또는 동등한 상태 속성으로 스크린리더에 전달되어야 한다.
- 상세 영역은 landmark(`role="region"` 또는 `<section>` + `aria-label`)로 구분되어야 한다.
- 페이지에는 최소 1개의 `<h1>`이 있어야 하고, 목록·상세 영역 각각에 `<h2>` 이상의 heading이 있어야 한다.
- 항목 선택 시 포커스가 예기치 않게 다른 곳으로 이동하지 않아야 한다(포커스는 클릭/Enter한 항목에 유지).

## 9. 임시 가정과 확정 결정의 구분

- **확정(DEC-001, DECISION_LOG.md)**: 상세 영역 = 오른쪽 고정 패널. Researcher 조사(RESEARCH_REPORT.md §3.1~3.4)로 근거 보강됨 — GitHub Inbox, herdr-dashboard, Linear 사이드바 모두 동일 패턴.

- 확정(사용자 원문 근거, 변경 불필요): 우선순위 3단계 P0/P1/P2, 상세 항목 4종(우선순위/리뷰 필요 여부/담당/다음 액션), mock 데이터 사용.
